### 3. Flink SQL `CREATE TABLE` statements

```sql
CREATE TABLE banking_transactions (
  account_id STRING,
  transaction_id STRING,
  transaction_time TIMESTAMP,
  amount DECIMAL(10, 2)
) WITH (
  'connector.type' = 'kafka',
  'connector.version' = 'universal',
  'connector.topic' = 'banking-transactions',
  'connector.startup.mode' = 'earliest-offset',
  'properties.bootstrap.servers' = 'my-cluster-kafka-bootstrap:9092',
  'scan.startup.mode' = 'latest-offset',
  'properties.group.id' = 'banking-transactions-group',
  'format' = 'json',
  'json.timestamp-format' = 'iso-8601/Basic',
  'json.ignore-parse-errors' = 'true',
  'json.fail-on-missing-field' = 'false'
);

CREATE TABLE banking_transactions_validated (
  account_id STRING,
  transaction_id STRING,
  transaction_time TIMESTAMP,
  amount DECIMAL(10, 2)
) WITH (
  'connector.type' = 'kafka',
  'connector.version' = 'universal',
  'connector.topic' = 'banking-transactions-validated',
  'connector.startup.mode' = 'earliest-offset',
  'properties.bootstrap.servers' = 'my-cluster-kafka-bootstrap:9092',
  'scan.startup.mode' = 'latest-offset',
  'properties.group.id' = 'banking-transactions-group',
  'format' = 'json',
  'json.timestamp-format' = 'iso-8601/Basic',
  'json.ignore-parse-errors' = 'true',
  'json.fail-on-missing-field' = 'false'
);
```

Justification:

1.  **Kafka Topic Configuration:**

    *   We create two Kafka topics: `banking-transactions` for the input data and `banking-transactions-validated` for the output data.
    *   Each topic has 16 partitions, a replication factor of 3 for high availability, and a retention period of 7 days.
    *   The `message.max.bytes` and `max.message.bytes` are set to 1 MB to match the expected average event size of 1024 bytes.
2.  **Flink Deployment Configuration:**

    *   We create a Flink deployment with 1 replica, 4 CPU, and 8 GB of memory per TaskManager.
    *   The Flink job is configured to use exactly-once end-to-end delivery with a checkpoint interval of 10 seconds.
    *   The Flink configuration is stored in a ConfigMap, which is mounted as a volume to the Flink container.
3.  **Flink SQL `CREATE TABLE` Statements:**

    *   We create two tables: `banking_transactions` for the input data and `banking_transactions_validated` for the output data.
    *   Both tables use the `kafka` connector with the `universal` version and are configured to use the `banking-transactions-group` consumer group.
    *   The `banking_transactions` table is configured to read from the `banking-transactions` topic, while the `banking_transactions_validated` table is configured to write to the `banking-transactions-validated` topic.
    *   Both tables use the `json` format with timestamp parsing and ignore parse errors.

The main values chosen are based on the provided requirements and assumptions:

*   **50,000 events/s**: We assume one Flink source subtask can process at most 20,000 events/s, so we need at least 3 source subtasks to handle the input rate. We also assume one Kafka partition can sustain at most 5 MB/s of produce traffic, so we need at least 3 partitions to handle the output rate.
*   **Below 100 ms end-to-end latency**: We choose a checkpoint interval of 10 seconds, which is a good trade-off between latency and throughput.
*   **Exactly-once end-to-end delivery**: We use the `EXACTLY_ONCE` checkpointing mode to ensure that all events are processed exactly once, even in the presence of failures.
*   **High availability**: We use a replication factor of 3 for both Kafka topics and 3 TaskManager replicas for the Flink job to ensure high availability.
*   **Durable checkpoint storage**: We use an S3 bucket as durable checkpoint storage for the Flink job.
