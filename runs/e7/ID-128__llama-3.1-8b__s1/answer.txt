### 3. Flink SQL `CREATE TABLE` statements

```sql
-- Create the source table
CREATE TABLE clicks (
  session_id STRING,
  timestamp BIGINT,
  event_name STRING,
  ...
) WITH (
  'connector.type' = 'kafka',
  'connector.version' = 'universal',
  'connector.topic' = 'clicks',
  'connector.properties.bootstrap.servers' = 'my-cluster-kafka-bootstrap:9092',
  'scan.startup.mode' = 'earliest-offset',
  'value.format' = 'json'
);

-- Create the sink table
CREATE TABLE clicks_enriched (
  session_id STRING,
  timestamp BIGINT,
  event_name STRING,
  ...
) WITH (
  'connector.type' = 'kafka',
  'connector.version' = 'universal',
  'connector.topic' = 'clicks-enriched',
  'connector.properties.bootstrap.servers' = 'my-cluster-kafka-bootstrap:9092',
  'connector.properties.acks' = 'all',
  'sink.partitioner' = 'range',
  'sink.partitioner.num.buckets' = 6
);

-- Define a SQL function to filter out malformed events
CREATE FUNCTION is_valid_event AS 'json' IS NOT NULL;

-- Define the SQL query to read from the source, filter out malformed events, enrich each event, and write to the sink
INSERT INTO clicks_enriched
SELECT
  session_id,
  timestamp,
  event_name,
  ...
FROM clicks
WHERE is_valid_event(event_name) = TRUE;
```

Main values:

*   **Input rate**: We assume an input rate of 20,000 events/s, which is the highest rate specified in the problem statement.
*   **End-to-end latency**: To achieve an end-to-end latency of below 1 s at p99, we configure Flink to use the EXACT-LATENCY checkpointing mode, which ensures that checkpoints are taken at fixed intervals (5 s in this case). This allows Flink to recover quickly from failures and maintain a consistent latency.
*   **Delivery guarantee**: To ensure at-least-once delivery, we configure the Kafka sink to use the `acks=all` setting, which requires all in-sync replicas to acknowledge the write before considering it successful.
*   **Retention**: We set the retention period for both topics to 7 days, as specified in the problem statement.
*   **Durability**: To ensure that both topics survive the loss of any single Kafka broker without losing acknowledged data, we configure the Kafka cluster to use the KRaft consensus protocol, which provides high availability and fault tolerance.
*   **Sizing**: We assume that one Kafka partition can sustain at most 5 MB/s of produce traffic, which is a reasonable assumption for a production environment. We also assume that one Flink source subtask can process at most 20,000 events/s, which is the input rate specified in the problem statement.
