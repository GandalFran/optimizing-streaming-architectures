### Justification of Main Values

1. **Kafka Topics Configuration**:
   - **Partitions and Replicas**: Both topics have 4 partitions and 3 replicas. The number of partitions is chosen to distribute the input rate of 5,000 events/s across the available Kafka brokers. Each partition can handle up to 5 MB/s, and with 4 partitions, we can handle up to 20 MB/s, comfortably supporting the 5,000 events/s (5,000 events * 512 bytes = 2.5 MB/s). The replicas ensure durability and availability, as the data is replicated across multiple brokers.
   
2. **Flink Deployment Configuration**:
   - **Task Slots and Parallelism**: Each TaskManager has 4 slots, and the default parallelism is set to 4, ensuring that the Flink job can process the input rate efficiently. This is based on the assumption that each source subtask can process up to 20,000 events/s, and with 4 subtasks, it can handle up to 80,000 events/s, which is more than sufficient for the 5,000 events/s input rate.
   - **Checkpointing**: Checkpointing is set to EXACTLY_ONCE mode with an interval of 10 seconds. This ensures fault tolerance and end-to-end consistency. The minimum pause between checkpoints is set to 1 second to minimize overhead.
   - **State Backend**: RocksDB is chosen as the state backend for its performance and durability.

3. **Flink SQL Table Definitions**:
   - **ad_impressions Table**: This table is configured to read from the `ad-impressions` topic. The `event_time` field is extracted from the metadata of the Kafka message.
   - **ad_impressions_enriched Table**: This table writes the enriched events to the `ad-impressions-enriched` topic. The enriched field is a placeholder for the derived fields that will be added during the enrichment process.

These configurations aim to meet the end-to-end latency requirement of less than 1 second at p99, while ensuring that the system is durable and scalable.
