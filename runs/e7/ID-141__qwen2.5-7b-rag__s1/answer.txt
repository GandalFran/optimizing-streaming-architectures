### Justification of Main Values

1. **Kafka Topics Creation**:
   - `app-logs` and `app-logs-parsed` topics are created with 8 partitions and a replication factor of 3 to ensure high availability and fault tolerance. This setup should handle the input rate of 20,000 events/s with sufficient throughput.

2. **Flink Configuration**:
   - **Checkpointing**: Set to exactly-once to ensure no duplicates and no data loss. Checkpoints are configured to be durable and efficient, using S3 for checkpoint storage.
   - **Parallelism**: Set to 8 to match the number of partitions, ensuring that data is evenly distributed and processed in parallel.
   - **State Backend**: RocksDB is chosen for its efficiency and durability. Memory-bounded is set to false to ensure data is not lost in case of a sudden increase in state size.
   - **Network Settings**: Send buffer size is set to 2 MB to ensure efficient network usage.

3. **Flink SQL Table Statements**:
   - **Source Table**: `app_logs` is configured to read from `app-logs` topic, using JSON format and the latest offset for startup.
   - **Sink Table**: `app_logs_parsed` is configured to write to `app-logs-parsed` topic, using the same format and partitioning strategy. Checkpointing is enabled for exactly-once guarantees, and the sink is set to use the same partitions as the source to ensure consistency.
   - **Transformation**: The `INSERT INTO` statement represents the core logic of the Flink SQL job, where events are read, transformed, and written to the output topic.
