```sql
-- Flink SQL CREATE TABLE statements for Kafka source and sink tables
CREATE TABLE ad_impressions (
  `campaign_id` STRING,
  `event_time` TIMESTAMP(3),
  `event_data` STRING,
  `event_type` STRING,
  `user_id` STRING,
  `ad_id` STRING,
  WATERMARK FOR `event_time` AS `event_time` - INTERVAL '5' SECOND
) WITH (
  'connector.type' = 'kafka',
  'connector.version' = 'universal',
  'connector.topic' = 'ad-impressions',
  'connector.properties.bootstrap.servers' = 'my-cluster-kafka-bootstrap:9092',
  'format.type' = 'json',
  'format.derive-schema' = 'true',
  'update-mode' = 'append'
);

CREATE TABLE ad_impressions_enriched (
  `campaign_id` STRING,
  `event_time` TIMESTAMP(3),
  `event_data` STRING,
  `event_type` STRING,
  `user_id` STRING,
  `ad_id` STRING,
  `derived_field1` STRING,
  `derived_field2` STRING
) WITH (
  'connector.type' = 'kafka',
  'connector.version' = 'universal',
  'connector.topic' = 'ad-impressions-enriched',
  'connector.properties.bootstrap.servers' = 'my-cluster-kafka-bootstrap:9092',
  'format.type' = 'json',
  'format.derive-schema' = 'true',
  'update-mode' = 'append'
);
```

Justification:

*   We create two Kafka topics (`ad-impressions` and `ad-impressions-enriched`) with 10 partitions each to handle the input rate of 5,000 events/s. This allows for a maximum produce traffic of 50 MB/s (10 partitions \* 5 MB/s per partition), which is above the required 2.56 MB/s (5,000 events/s \* 512 bytes per event).
*   We set the replication factor to 3 for both topics to ensure that data is not lost in case of a single broker failure.
*   We configure the Flink job to use 3 TaskManager pods with 4 CPU cores and 8 GiB of memory each. This allows for a total of 12 CPU cores and 24 GiB of memory, which should be sufficient to handle the input rate.
*   We set the parallelism of the Flink job to 10, which matches the number of Kafka partitions. This allows for optimal processing of the input data.
*   We configure the Flink job to use a fixed-delay restart strategy with 3 attempts and a delay of 10 seconds. This allows the job to recover from failures and ensures that data is not lost.
*   We set the checkpointing interval to 10 seconds and the checkpointing timeout to 1 minute. This allows for frequent checkpoints and ensures that data is not lost in case of a failure.
*   We use the `RETAIN_ON_CANCELLATION` checkpoint retention policy to ensure that checkpoints are retained even after the job is cancelled.
*   We create two Flink SQL tables (`ad_impressions` and `ad_impressions_enriched`) to read from and write to the corresponding Kafka topics. We use the `kafka` connector with the `universal` version and configure the bootstrap servers, topic, and format accordingly.
